Role selectors across the app

An inventory of every place where one or more roles are selected — the purpose of each, how it is built, how it behaves UX-wise, and the gaps that need to be settled before unifying them.

Target requirements

  • Lists all roles the user is allowed to see.
  • A switch between single and multiple selection.
  • Roles can be de-selected again.
  • Filter/search by typing.
  • Full keyboard control.
  • "Rich" role display: icon + name, as in SingleRoleBadge.tsx.

Family A — Popover of role badges + chips below

Visually near-identical, written independently three times, plus a fourth variant with a different payload. Shared model: a trigger opens a popover listing SingleRoleBadge buttons; picking one adds it; selected roles appear as chips underneath; the value reaches the form via hidden inputs.

A1 · WikiRoleSelector Base UI popover

File
modules/wiki/components/WikiRoleSelector.tsx

Read, edit and admin roles of a wiki page; and the role for the "role members" block.
Used in

UX
Trigger reads "Rolle hinzufügen" / "Rolle auswählen". The popover opens on hover (openOnHover defaults to true, 50 ms delay) and takes no focus when opening (initialFocus={false}, PopoverBaseUI.tsx:139). Already-selected roles are not marked in the list, and clicking them again is a no-op (no toggle). Removal is only possible through the chip's trash button.

Shared building blocks

  • SingleRoleBadge.tsx — icon + name + level progress bar, with its own detail popover. Inside a picker it needs withPopover={false}, otherwise buttons get nested (A1 does this, A2/A3/A4 do not).
  • RolesContext.tsx, provided in app/app/layout.tsx:52 — already holds every visible role client-side, including icon, thumbnail and inherits. SingleRoleBadge resolves names from it and renders null for any role not in it (SingleRoleBadge.tsx:81).
  • PopoverBaseUI.tsx (Base UI) and Radix Popover — both popover stacks are in use at once, partly for the very same pattern.
  • YesNoCheckbox.tsx — the checkbox look in B1 and B3.

Problems found

  1. Blank rows in the SILC picker. A3 lists roles from getRolesForSalaries, which is built on getRoles() (all roles, no visibility filter, server/api/routers/silc/getRolesForSalaries.ts:36), but renders them through SingleRoleBadge, which returns null for roles outside the RolesContext. Anyone with silcSetting;manage but limited role visibility sees clickable, empty list entries.
  2. Same issue in InheritanceForm (B2). getRoles() + SingleRoleBadge ⇒ invisible roles show up as a bare checkbox with no label.
  3. Six data sources for "the roles I may see". Nothing enforces which one is correct where. getAssignableRoles is used at exactly one site.
  4. Redundant fetching. A1 and A2 fetch roles.getVisibleRoles over tRPC although RolesContext already holds that exact list in memory.
  5. Portal container ref read during render (A2 and A4): popoverPortalRef.current is null on the first render pass, so the assignment is timing-dependent.
  6. No de-selecting from the list in A1/A2/A4: selected roles are neither marked nor toggleable; removal only works through the chip's trash button.
  7. Inconsistent close-on-select. A3 closes on pick, A1/A2/A4 do not — A1 not even in single mode.
  8. Keyboard. A1–A4 are tab-through button lists: no arrow keys, no typeahead, no focus restoration after Escape; A1 takes no focus at all when opening. Only the native selects (C) and the unused comboboxes (D) are properly keyboard-operable.
  9. Loading and error states. Only B1 has both. A1–A4 silently render an empty list on error.
  10. Hardcoded German strings everywhere; next-intl is used only in UpdateRolesForm.
  11. No test coverage for any role picker (the only e2e file is apps/playwright/tests/smoke.spec.ts).

Consequences of the rich display (icon + name)

This requirement is the decisive reason why the existing combobox filters (family D) cannot simply be adopted as-is, and it forces several follow-up decisions:

  • The item model has to open up. D works with {value, label} strings and renders title={item.label} plus truncate. Badges need either a render prop per option/chip or a role-specific item model. The plain text value is still required — for search, for title tooltips and for typeahead matching.
  • SingleRoleBadge returns null when the role is not in RolesContext. Once the unified selector renders badges everywhere, the data-source question becomes mandatory: either every picker uses the visible set, or the badge needs a fallback for unknown roles (see problems 1 and 2).
  • Nested buttons. The badge ships its own popover with a <button>. Inside options and chips withPopover={false} is required — currently forgotten in A2, A3 and A4.
  • Level progress and assignment actions in the badge (level +/−, delete assignment) make no sense inside a picker and should be suppressed there. Open question: does the selector need a reduced badge variant?
  • Layout. A badge is h-8 tall and carries a 24 px icon — noticeably taller than a line of text. That affects tight contexts (the SILC salary grid row, chip rows in the wiki modal, the filter sidebar) and how many options fit into the max-h-96 popover.
  • Image loading. Icons come from S3 via next/image, partly unoptimized for SVG/GIF, with loading="lazy". In a scrollable, filtered list that means visible pop-in; a placeholder is needed so the list does not jump while typing (showPlaceholder already exists).
  • Search highlighting vs. badge. B1 currently underlines the matched characters in the role name (underlineCharacters). If the name lives inside the badge from now on, the badge must accept an already-rendered name node — otherwise the highlighting is lost.
  • Consistency win. B1 and B3 rebuild icon + name by hand today, including their own S3 URL construction and unoptimized logic. Unifying on the badge removes those duplicates.
  • Regression risk for family C. C1–C3 are plain text selects today; switching them to badges is a genuine visual improvement, but costs the native keyboard and mobile behaviour.

Open decisions (what the requirements do not cover yet)

Data scope

  • Which set of roles? "All visible ones" fits wiki and tasks, but citizen assignment needs the assignable roles, while the rule builder and inheritance need all roles. This has to be an explicit prop or data-source contract, not a default.
  • Disabled entries with a reason. B1 locks individual roles based on permission — the new selector needs disabled per option plus an explanation.
  • Pseudo options. C3 needs a * "Alle" entry; C1/C2 must never be empty.
  • Fetch itself, or take roles as a prop? Since RolesContext already holds the visible set, a context-first component with an optional override would save three network round-trips.

Value & form integration

  • Output contract. In use today, in parallel: a hidden input with a configurable name (A1), with a fixed name (A2/A3), onChange (A3/A4), checkbox names role_<id> (B1) and roles (B2), URL query parameters (B3), values encoded into input names (C3), and React state → node attributes (C1/C2). The new selector should support at least three modes: uncontrolled with hidden inputs, controlled via value/onChange, and nuqs/URL-bound.
  • Save semantics. B1 auto-saves with a debounce, B2/A2 have a save button, B3 navigates immediately. Does the selector own any of this, or stay purely presentational?
  • Required vs. optional, and what "empty" means. Empty means "private page" in the wiki, "no restriction" for tasks, and "invalid" for career nodes.
  • Minimum/maximum number of selections.

UX details

  • Is the single/multi switch a prop or a user-facing toggle? Today the mode is fixed by the call site everywhere; a runtime toggle really only makes sense in filters.
  • Close after selection — for single vs. multiple selection.
  • Mark already-selected roles in the list and allow de-selecting them there too (in addition to the chips).
  • Ordering & grouping. Alphabetical everywhere today. Should selected roles float to the top? Group by anything (e.g. inheritance)?
  • Search behaviour. Fuzzy (B1, fuse.js, with match highlighting) vs. substring (D). The highlighting is worth keeping.
  • Long lists. Everything caps at max-h-96 and scrolls; no virtualization. How many roles realistically exist?
  • Empty-state copy ("Keine Treffer", "no visible roles").
  • Loading and error presentation — define it once, in line with the existing wiki rule of "no silent failures".
  • Placement inside modals, React Flow and the wiki editor — the portal/z-index problem A2 and A4 work around by hand today. In the wiki editor the selection also has to survive collaborative re-renders.
  • Mobile/touch. Hover-to-open (A1) does not work on touch; the native selects (C) currently offer the best mobile experience of the lot.
  • Keyboard specifics: roving arrow keys, Home/End, typeahead, Enter/Space to toggle, Backspace removing the last chip, Escape closing and returning focus, and focus restoration after removing a chip (removing the last chip currently destroys the focused element).
  • Accessibility: an accessible name for the whole widget, aria-multiselectable, announcing selection changes, and an actually visible label (B1's label is display:none today).
  • i18n: decide whether the new component moves to next-intl or stays with German literals.

Migration

  • C1/C2/C3 get keyboard and mobile behaviour for free from the native <select>. Replacing them with a custom combobox is a regression as long as keyboard support is incomplete — worth deciding whether those three migrate at all, or only families A and B.
  • A4 (CitizenInput) selects roles but produces citizens. Whether it becomes the same component with a different onChange or stays out of scope needs to be settled.
  • B1 depends on filtered-out options staying mounted, because the form submits all checkboxes. A selector that unmounts while searching breaks that model — so the selection has to live in state, not in the DOM.
